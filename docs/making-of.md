# 製作過程: 用 Claude Code 從道德經 skill 延伸出 sunzi skill

這份紀錄整理自一次 Claude Code session, 橫跨數天. 起點是兩個檔案: 道德經專案的產品構想 `Develop.md`, 以及一份《孫子兵法》原文與白話 `The Art of War.md`. 終點是一個經過查證, 盲測與驗證的 Claude Skill.

每一段後面的 "Claude Code 做了什麼", 說明這個環節值得注意的地方.

## 1. 起點: 只丟一個檔案, 選取一行字

使用者沒有下指令, 只用 `@` 引用了道德經專案的 `Develop.md`, 並在另一個檔案裡選取了標題 "孫子兵法". Claude 讀了原文檔的目錄與原文段落, 確認有十三篇加一個附錄, 然後只問一個問題: 想做什麼? 使用者選了 "寫孫子版 Develop.md".

### Claude Code 做了什麼

- 使用者意圖不明時, 先讀材料, 再用一個選擇題確認, 不自行假設要做到哪一步.

## 2. 第一版構想, 以及把引文當成要查證的東西

Claude 比照道德經的結構, 寫出孫子版 Develop.md: 5 個心智模型, 8 類情境, 引文規則, 風險, 反駁檢查點, 驗收方式. 寫完後用腳本把文中 22 段引文逐字比對原文, 全部對得上.

它也指出兩個道德經版沒有的問題:

- 白話翻譯是 Claude 寫的意譯, 不能當成 "孫子說".
- 附錄問答篇出自後世輯佚, 按語自己就寫 "不似孫武語", 不能列入金句.

### Claude Code 做了什麼

- 產品文件裡順手引的原文也用程式查證, 不靠記憶.
- 主動找出來源資料本身的可信度問題.

## 3. 擴大範圍到商業競爭, 整理原文

使用者移動了原文檔, 並要求把範圍從個人職涯放大到商業競爭與企業經營. Claude 先找到檔案的新位置, 重寫 Develop.md: 開頭故事改成對手降價三成, 情境改成開戰與否, 消耗戰, 組織與授權等經營情境, 風險段加入商業上的越界做法, 例如營業秘密, 不實宣傳, 聯合定價.

接著用腳本從原文檔產生 `references/sunzi.md`: 91 段原文逐段編號 (例如 3.8 是謀攻第三第 8 段), 前面放 40 句的情境索引. 40 句都用程式確認是原文段落的子字串.

之後使用者手動改了 sunzi.md. Claude 重新產生一份原始版本做 diff, 找出兩處修改 (附錄標題拿掉 "存疑", 刪掉錯字修正紀錄), 確認引文沒有受影響, 也指出 "存疑" 的提醒只剩使用規則裡一處.

### Claude Code 做了什麼

- 原文整理用腳本產生, 不手抄, 所以能保證 91 段一段不漏.
- 使用者手改檔案後, 用 diff 說清楚改了什麼, 而不是只說 "我看過了".

## 4. 測試情境, 以及第四種分支

使用者要 10 到 15 個經營卡點測試情境. Claude 寫了 14 題, 每題有開場白, 預期卡點, 可用原文, 紅線, 反駁與預期分支, 並刻意混入 "對方其實不是敵人" 和 "使用者想要越界手段" 的案例.

寫測試時它發現, 使用者要求營業秘密或對員工說謊時, 不屬於原本的三種反駁分支, 因為問題不在判斷對錯. 於是新增代號 X: 直接拒絕, 說明原文為何不能這樣延伸, 使用者再用 "大家都這樣做" 反駁時照 B 處理. 使用者同意後, X 也補進 Develop.md.

### Claude Code 做了什麼

- 從寫測試的過程中找出設計缺口, 回頭補進規格.

## 5. 盲測的設計, 以及一次中止

受測對象是一個子代理, 只能讀 Develop.md 和 sunzi.md, 看不到測試資料夾. 反駁分兩輪送出, 模擬真實對話.

第一次盲測, 子代理寫到第三題時被安全分類器中止. 子代理建議另派一個新代理重跑. Claude 沒有照做, 而是回報使用者: 換一個代理重跑同樣內容, 等於繞過中止, 這應該由使用者決定. 使用者選擇分批重跑, 越界題各自單獨一批. 之後的所有盲測都沒有再被中止.

只寫完的兩題也暴露一個問題: 子代理把 Develop.md 開頭的比喻和收尾問句原句照抄. 原因是開頭故事 "對手降價三成" 和測試題 S01 幾乎一樣. 使用者決定先改文件: 開頭故事換成測試集沒有的 "大客戶要求獨家", 並寫明文件裡的故事, 比喻, 問句都只是示範. 評分表也新增 "無套路" 一欄.

### Claude Code 做了什麼

- 被安全機制中止時, 不自行繞過, 把決定交回使用者.
- 看出照抄的根本原因是示範和測試題重疊, 不只是 "示範寫得太具體".

## 6. 三輪調整

| 輪次 | 修改 | 主測試集結果 |
| --- | --- | --- |
| 第一輪 | 無 | 68/70, 2 格待議 |
| 第二輪 | 收尾不必是問題, 300 字目標, 引文格式統一, SOP 定義涵蓋列選項與代寫台詞 | 68/70, 1 待議, 1 不通過 |
| 第三輪 | 開場就看得出不適合用兵法時第一則就說, 法規風險主動提醒 | 70/70 |

第一輪 23 則回覆幾乎都用 "我想問你一件事" 收尾, 平均 527 字. 第二輪固定句式歸零, 平均 261 字, 但 S14 (創業第三年很累) 退步: 回覆變短後, 少了 "這件事不適合用兵法看" 的判斷. 第三輪補上後全數通過.

每次修改 Develop.md 時, Claude 都檢查新加的例句有沒有洩漏測試答案. 例如草稿裡的 "你守的是一片正在縮小的地" 是上一輪 S06 的原句, 改成和開頭故事同一情境的例子後才定稿.

### Claude Code 做了什麼

- 每輪都和前一輪量化對照, 字數, 句式, 收尾方式都有數字.
- 改規格時防止把測試答案寫進規格, 避免分數虛高.

## 7. 第一組 holdout

三輪都用同一組 14 題, 有過度擬合的風險. Claude 建議另寫 8 題不同產業的驗證情境, 規定不能根據結果回頭修改. 結果 39/40, 主要行為有推廣到新情境, 但回覆長度和法規提醒的份量比熟悉的題目鬆.

使用者選擇就此定稿, 並問下一步是不是寫 skill.

## 8. 用 skill-creator 做成 skill

Claude 載入 skill-creator, 比照道德經專案的結構建立 `.claude/skills/sunzi/`: SKILL.md, 5 個心智模型, 40 句情境, 5 則示範對話, 原文副本, 以及檢查引文的 `scripts/verify_skill.py`.

兩個刻意和道德經專案不同的地方:

- 測試情境不放進 skill 資料夾, 避免模型回應時讀到預期答案.
- 寫草稿時發現幾個例子和測試答案重疊, 例如 "血壓計說讀數, 印刷業說網點", 全部換掉. 也坦白說明: SKILL.md 是在看過第一組 holdout 後寫的, 那 8 題已經不算 "沒看過".

### Claude Code 做了什麼

- 把寫給人看的產品文件, 改寫成寫給模型的指令, 保留三輪測試調出來的所有規則.
- 主動揭露自己的資訊污染, 並提出補救: 另寫一組驗證情境.

## 9. 有無 skill 對比, 以及第二組 holdout

照 skill-creator 的流程, 挑 4 題跑 "載入 skill" 與 "不載入 skill" 兩個版本, 用 skill-creator 的檢視器呈現. 結果通過率 95% 對 55%. 差距最大的是 S14: 不載入 skill 時, 模型把 "累" 分成四類並列出選項, 沒有建議專業協助. 使用者在檢視器上給 4 題正面評價, 沒有修改意見, 所以沒有改 skill.

接著寫第二組 holdout, 8 題, 產業避開所有先前用過的情境與示範. 這是第一次直接用 skill 本身做驗證, 結果 40/40, 第一則平均 269 字.

## 10. 觸發描述: 工具在 Windows 上壞了

skill-creator 的描述優化腳本用 `select` 讀取子行程輸出, Windows 不支援, 所以第一次執行時所有查詢都失敗, 分數全是假的. Claude 發現 "0.0 秒完成" 不合理, 查 log 找到錯誤, 停掉迴圈, 在 scratchpad 的副本裡改用讀取執行緒. 它也發現另一個問題: 這個專案已經裝了真的 sunzi skill, 查詢會觸發真的 skill 而不是測試用的副本, 所以改在一個空的專案目錄執行.

修好後的迴圈跑到第三輪時中斷 (推測是用量額度用完). 已跑完的結果顯示, 優化器改出的描述越來越強勢, 最後變成 "強制使用" 和 "任何商業難題的預設顧問", 召回率只從 11% 升到 22%. Claude 不建議採用, 因為這會讓 skill 攔下幾乎所有商業對話, 違背它 "一個角度" 的設計.

最後改用低並行, 長逾時的方式, 比較原本描述和一個折衷版:

| 指標 | 原本的描述 | 折衷版 |
| --- | --- | --- |
| 該觸發: 20 次中觸發次數 | 9 次 | 7 次 |
| 不該觸發: 誤觸發 | 0 次 | 0 次 |

折衷版沒有比較好, 保留原本的描述. 也釐清了上週低分有一部分是逾時造成的測量雜訊. README 寫明: 需要這個視角時, 用 `/sunzi` 呼叫最可靠.

### Claude Code 做了什麼

- 從不合理的數字 (0.0 秒, 全部 0 分) 判斷是工具壞了, 不是描述不好.
- 修工具時改副本, 不動使用者安裝的 skill-creator.
- 自動化工具給出的最佳解違背產品設計時, 說明理由並建議不採用.

## 11. 限制

- 所有評分都由開發過程中的 Claude 執行, 評分者看過預期答案, 受測者沒有.
- 每題通常只跑一次, 差距只能當方向參考.
- 自動觸發率約一半, 主要受限於 Claude 遇到能直接回答的問題時不調用 skill.
- 法規提醒偏頻繁, 第二組 holdout 8 段對話中有 6 段出現. 列為上線後觀察項目.
- 真實使用者的回饋尚未納入.

## 12. 檔案與紀錄

- 產品構想: `Develop.md`
- 測試情境: `tests/scenarios.md`, `tests/holdout.md`, `tests/holdout-2.md`
- 每次盲測的評分與完整對話: `tests/runs/`
- skill-creator 的對比測試與觸發測試: `sunzi-workspace/`
